# Waad (وعد) — bilingual HR + ERP for Saudi SMEs

Owner: Abdulaziz Al-Fawzan (HR professional, Riyadh). Reply in Arabic, concise, direct, show trade-offs.
Everything is bilingual Arabic (RTL, default) + English, must follow Saudi Labor Law, work on desktop + mobile.
Free-tier only (Supabase free plan + GitHub). One account = one company. Platform admin sees only subscription metadata, never company data.

## What this is
A single-file vanilla-JS web app (no framework, no bundler) with a Supabase (Postgres + PostgREST + Auth) backend.
The whole frontend is concatenated into ONE self-contained HTML file and hosted statically.

## Layout
- `app/src/*.js` + `app/src/style.css` — the source. Each module registers routes on `VIEWS['#/...']`.
- `app/build.py` — concatenates `app/i18n/en.tsv` (as a `const EN = {...}`) + an EXPLICIT list of `src/*.js` into `app/waad-app.html`. The file list is hard-coded in build.py (not a glob) — add new src files there.

- `supabase/migrations/NNNN_*.sql` — ordered DB migrations (RLS on every table; `has_role(company, roles[])` gates access).
- `supabase/tests/run.sh` — spins a throwaway Postgres, applies all migrations + test files, must end `… 0 failed`.
- `app/tests/e2e_app.py` — Playwright end-to-end against the dev server.

Database reads leave no trace, so screens call `accessNote(kind, {emp, ref, label})` → `access_note` (member only, own record skipped, same item within 10 minutes counted once, 300/hour); company exports are logged on the server (`access_add`). A direct API read by an authorized user is not captured: do not describe it as logging every read.
- Employee sign-in (0129, bio.js): «نسيت كلمة المرور» on the staff screen → anon `staff_password_help` (same answer whether the number exists, 5 per IP per 15 minutes) → `staff_password_requests` for that company's HR (bell, phone, banner on «الموظفون»; `reset_staff_password` closes it). «تذكر دخولي» (default on; off = session ends with the browser). Fingerprint/face = WebAuthn platform authenticator as a LOCAL unlock of the saved session (`waad.bio`, relocks after 15 minutes away): not server authentication, unavailable after sign-out, and a new domain needs re-enabling; the iPhone Capacitor shell still needs a native Face ID plugin.
- Recruitment messages (engage.js `candidateMessage` / `candidateText`, button «مراسلة المرشح» saves the form first): WhatsApp, Gmail, Outlook and mail app go to the candidate's number and e-mail; subject and text by kind (interview by type, offer, documents, regret, general) and language. `waPhone` accepts Arabic digits and international numbers with a country code.
- Announcements outside the system (engage.js `annSend`, opens after publishing and from «بريد وواتساب»): audience = in-service employees (all or the department); Gmail / Outlook / mail app links with the addresses in BCC, split by `annMailBatches` (50 per message, URL length limits; a text too long for a link is copied to paste); WhatsApp one message per employee (`annWaText`, long text cut with a link to the system; progress kept on the device). HR presses send from their own mailbox/WhatsApp: Waad sends nothing and must not claim automatic sending from the company's address or number.
- Leave (0130): «إجازة سنوية خارجية» is the form option `annual_out` = `sub annual` + payload `abroad`/`dest` (same balance). Sick: `sick_preview` / pure `sick_split` show the Art. 117 split (payroll deduction stays `sick_deduction`); trigger `requests_leave_guard` refuses a sick-leave number already on another live request of the company, strips forged `seha`, clears it when the number changes, and blocks approval when the result is «bad». Seha has no public employer API and its inquiry page (`SEHA_INQUIRY`: service code + ID) is protected against automated use: Waad never queries it; HR checks by hand and records the result (`sick_verify`, GUC `waad.seha`). Do not claim automatic Seha verification.
- Attendance by phone or website (`clock`, «حضوري»); a fingerprint device is optional. `employees.att_any_place` (0131, set by HR in the employee file) skips the work-site check for that employee and the browser location request.
- Shift library (attendance.js `SHIFT_GROUPS` / pure `shiftLibrary`, card «ورديات جاهزة» in attendance settings, and `shiftOpts` / `shiftPick` in every shift picker: employee file, department, roster): ready shifts every hour plus office half-hour, split and part-time types; ticking them or saving one from a picker makes an ordinary `shifts` row with a Ramadan time (work capped at 6 hours + the same break). All stay within `shift_guard` (Art. 98) and a break above 5 hours of work (Art. 101); no 12-hour shifts.

- ZATCA Phase 2 (Fatoora) — `docs/ZATCA_PHASE2.md`. ## Deploy — automated by CI (this replaces all manual steps)
`.github/workflows/deploy.yml`: on push to `main` it runs the DB tests + i18n check + build + browser tests, then (main only) applies NEW Supabase migrations and publishes the app.
One repository secret the owner adds once (Settings → Secrets and variables → Actions):
- `SUPABASE_DB_URL` — Supabase → Project Settings → Database → connection string (URI, session pooler).
Publishing needs no token: the deploy job commits the built app to `site/app/index.html` on `main` with its own `GITHUB_TOKEN` (commit tagged `[skip ci]`), and GitHub Pages serves `main` /.
First deploy treats migrations up to `supabase/BASELINE` as already applied by hand and applies the rest.
After that: edit source → build + tests green → commit → push. CI migrates Supabase and deploys. No manual SQL editor, no manual file upload.
