# دراسة: الربط مع «فاتورة» — المرحلة الثانية (زاتكا)

> دراسة فقط، لم يُنفَّذ منها شيء بعد. تاريخها 2026-11-11. الأرقام والمواعيد من مصادر ثانوية (أبرزها EY) — تُراجَع على zatca.gov.sa قبل الاعتماد.

## 1. لماذا هي ضرورية الآن
- **الموجة 25:** حدّ الإيرادات نزل إلى **187,500 ريال** (كان 375,000 في الموجة 24)، لأي سنة من 2022 إلى 2025، وموعد الربط **1 فبراير 2027**. زاتكا تبلّغ المكلّفين قبل موعدهم بستة أشهر على الأقل بالبريد والرسائل.
- حدّ التسجيل الإلزامي في الضريبة 375,000 — يعني عملياً **كل منشأة مسجّلة في الضريبة إما داخلة الآن أو داخلة في فبراير 2027**.
- وعد اليوم يطبع رمز QR (المرحلة الأولى) فقط. أي عميل مسجّل في الضريبة يستخدم وعد للفوترة سيحتاج الربط قريباً، وإلا سيضطر لنظام آخر للفواتير.
- عملاء الموارد البشرية فقط (بدون فوترة) لا يتأثرون.

## 2. ماذا تتطلب المرحلة الثانية (مختصر تقني)
| المطلب | المعنى |
|---|---|
| **صيغة XML (UBL 2.1)** | كل فاتورة/إشعار دائن/مدين يُولَّد ملف XML بالمواصفة السعودية |
| **تسجيل وحدة الفوترة (EGS)** | العميل يولّد رمز OTP من بوابة فاتورة ← النظام يرسل طلب شهادة (CSR) ← يحصل على شهادة امتثال ← يجتاز 3 مستندات تجريبية ← شهادة إنتاج (Production CSID) |
| **مفتاح خاص لكل منشأة** | منحنى secp256k1، لا يخرج من الخادم أبداً |
| **ختم تشفيري** | الفاتورة المبسطة تُوقَّع رقمياً (XAdES) |
| **سلسلة التجزئة** | كل فاتورة تحمل تجزئة الفاتورة السابقة (PIH) وعدّاداً تسلسلياً (ICV) — لا فجوات ولا تعديل |
| **QR بـ 9 حقول** | بدل 5 حقول الحالية (يضاف التجزئة والتوقيع والمفتاح العام وتوقيع الشهادة) |
| **التصريح (Clearance)** | الفاتورة الضريبية (لمنشأة لها رقم ضريبي) تُرسل لزاتكا **قبل** تسليمها للمشتري، وتعود مختومة |
| **الإبلاغ (Reporting)** | الفاتورة المبسطة (للأفراد) تُبلَّغ بعد إصدارها (المتداول: خلال 24 ساعة — يُتحقّق منه) |
| **لا إلغاء** | الفاتورة المُبلَّغة لا تُلغى؛ التصحيح بإشعار دائن أو مدين مرتبط بها |

## 3. وضع وعد اليوم
موجود ويُبنى عليه:
- الرقم الضريبي والسجل التجاري و**العنوان الوطني** للمنشأة والعملاء (0048).
- فاتورة ضريبية / مبسطة حسب وجود رقم ضريبي للعميل، وQR المرحلة الأولى (`qr.js`).
- **الإشعارات الدائنة** موجودة وغير قابلة للتعديل (0003).
- ترقيم الفواتير لكل منشأة، ومعرّف UUID لكل فاتورة.

ناقص:
1. لا يوجد XML ولا توقيع ولا سلسلة تجزئة ولا عدّاد ICV.
2. **إلغاء الفاتورة (`void_sales_invoice`) مسموح** — يجب منعه بعد الإبلاغ وتحويله لإشعار دائن.
3. لا يوجد **إشعار مدين**.
4. لا يوجد خادم: التطبيق صفحة واحدة + قاعدة بيانات. المفتاح الخاص والاتصال بزاتكا **لا يصح أن يكونا في المتصفح**.
5. لا توجد حالة للفاتورة مع زاتكا (معلّقة / مقبولة / مقبولة بتحذيرات / مرفوضة) ولا إعادة محاولة.

## 4. التصميم المقترح (ضمن الخطة المجانية)
**الخادم: Supabase Edge Functions** (مجانية حتى 500 ألف استدعاء شهرياً — تكفي بفارق كبير).

```
المتصفح ── يرحّل الفاتورة ──► Postgres: يحجز ICV + PIH بقفل، الحالة "pending"
                                   │
                                   ▼
                     Edge Function «zatca» (Deno)
         يبني XML ← يحسب التجزئة ← يوقّع (المبسطة) ← QR بـ 9 حقول
                                   │
                ┌──────────────────┴──────────────────┐
         فاتورة ضريبية (B2B)                    فاتورة مبسطة (B2C)
         Clearance فوري                         Reporting (فوري، وإن فشل يُعاد)
                └──────────────────┬──────────────────┘
                                   ▼
          يحفظ XML المختوم + الرد + الحالة ← المتصفح يطبع الفاتورة بالـ QR الجديد
```
- **المفتاح الخاص والشهادة:** في Supabase Vault (مشفّرة)، تقرؤها الدالة فقط بصلاحية الخادم.
- **التوقيع:** مكتبة `@noble/curves` (secp256k1، JavaScript خالص يعمل في Deno). طلب الشهادة (CSR) يُبنى بمكتبة ASN.1 بدل OpenSSL. مكتبات جاهزة للاستئناس: `zatca-xml-js` (المبسطة + التسجيل، تعتمد OpenSSL للـ CSR فقط).
- **إعادة المحاولة:** نفس المؤقّت الموجود (cron-job.org كل 10 دقائق) يعيد إرسال المعلّق.
- **التحقق:** أداة زاتكا الرسمية للتحقق من XML (SDK) تُشغَّل في CI على عيّنات، والاختبار على بيئة **المحاكاة** (simulation) قبل الإنتاج.
- **في الواجهة:**
  - الإعدادات ← «الربط مع فاتورة»: العميل يلصق OTP من بوابة فاتورة، والنظام يكمل التسجيل والاختبارات الثلاثة تلقائياً.
  - شارة حالة على كل فاتورة، وزر «إعادة الإرسال»، وتنبيه للمرفوضة مع سبب زاتكا.
  - زر «إلغاء» يصير «إصدار إشعار دائن» بعد الربط.

## 5. المراحل المقترحة
| # | المرحلة | الناتج |
|---|---|---|
| 1 | قاعدة البيانات | ICV + PIH + حالة زاتكا + حفظ XML، منع الإلغاء بعد الإبلاغ، إشعار مدين، اختبارات |
| 2 | مولّد XML + التجزئة + التوقيع + QR | دوال نقية مع اختبارات، ومطابقة أداة التحقق الرسمية |
| 3 | دالة الخادم + التسجيل (OTP ← CSID) | على بيئة المحاكاة |
| 4 | التصريح والإبلاغ وإعادة المحاولة | فواتير وإشعارات دائنة ومدينة |
| 5 | الواجهة + الطباعة بالـ QR الجديد | معالج الربط، الحالات، التنبيهات |
| 6 | تجربة على منشأة حقيقية (رقم ضريبي حقيقي، بيئة الإنتاج) | قبل التسويق |

### حالة التنفيذ
- **المرحلة 1 (قاعدة البيانات) — تمت** (0078): التسلسل، منع الإلغاء، الإشعار المدين، مخزن المفاتيح.
- **المرحلة 2 (بناء الفاتورة والتوقيع) — تمت** (`supabase/functions/_shared/zatca.ts` + اختباراتها في CI): التجزئة تطابق أداة زاتكا الرسمية، وبيئة مطوّري زاتكا قبلت (بقواعدها الحالية، بلا تحذيرات) الفاتورة والإشعار الدائن والمدين المبسطة (REPORTED) والضريبية (CLEARED)، وبنود نسبة الصفر بسبب الإعفاء. ملاحظة: نسخة الأداة المنزّلة (3.0.8 – 2022) قديمة؛ المرجع هو فحص بيئة زاتكا.
- **المرحلة 3 (دالة الخادم + الربط) — تمت** (0079، `supabase/functions/zatca`، `_shared/csr.ts`، `_shared/fatoora.ts`): طلب الشهادة يُبنى داخل الخادم (secp256k1 بدون OpenSSL)، والربط كامل جُرّب على بيئة مطوّري زاتكا: OTP ← شهادة امتثال ← 6 مستندات (3 CLEARED + 3 REPORTED) ← شهادة إنتاج. يربط المالك أو المدير فقط، والمفتاح الخاص لا يُقرأ إلا من الخادم. نشر الدالة يحتاج السرّ `SUPABASE_ACCESS_TOKEN` في GitHub.
- البنود بنسبة صفر تحتاج **سبب إعفاء** (رمز VATEX) — يُضاف للأصناف في الواجهة (المرحلة 5).

## 6. ما يلزمك أنت (المالك)
1. **رمز وصول Supabase** (`SUPABASE_ACCESS_TOKEN`) كسر في GitHub حتى ينشر CI دوال الخادم تلقائياً — مرة واحدة.
2. **حساب على بوابة مطوّري فاتورة** (مجاني) للبيئة التجريبية.
3. **منشأة حقيقية مسجّلة في الضريبة** تتعاون للاختبار النهائي (أو منشأتك إن كانت مسجّلة).
4. قرار: هل تسجّل وعد في **قائمة مزوّدي الحلول** لدى زاتكا؟ القائمة استرشادية وليست شرطاً للعمل (حسب المصادر) — يُتحقّق منها.

## 7. البديل
وسيط مدفوع (API جاهز للمرحلة الثانية) — أسرع، لكن له رسوم على كل فاتورة أو شهرية، وبيانات فواتير العملاء تمرّ بطرف ثالث. لا أنصح به مع سياسة «الخطة المجانية» وحساسية البيانات.

## 8. مخاطر
- تفاصيل XML والتوقيع دقيقة جداً (أكثر أخطاء المطوّرين في منتدى زاتكا: «التجزئة لا تطابق»). العلاج: أداة التحقق الرسمية في CI من اليوم الأول.
- انقطاعات بوابة زاتكا وحدود الطلبات — لذلك الطابور وإعادة المحاولة.
- التخزين خارج المملكة حالياً (اليابان) — يُراجَع موقف حفظ الفواتير الإلكترونية مع نقل التخزين (ديسمبر 2026).
- حجم XML (~10–20 ك.ب للفاتورة) — يكفي الخطة المجانية لعشرات آلاف الفواتير، ومع أول عميل يدفع تنتقل لخطة Pro.
